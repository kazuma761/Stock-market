What would have caught the "None" bug?

One run, scanned for the durable changes that would have prevented what went wrong — not the code fixes, the system fixes.

Target: the slim-stock-pipeline run Agent: Claude Code 5 findings · 2 honest non-findings

The headline

This run shipped a high-severity bug that the plan itself predicted in writing — and no part of the AI layer stood between the prediction and the defect.

The plan marked a spike BLOCKING. It couldn't run. The implementation substituted an assumption, wrote its test doubles from documentation instead of captured payloads, and the assumption was wrong in exactly the way the plan warned about.

  1. The plan recorded the risk verbatim. "Assumed — OVERVIEW returns non-empty Name and MarketCapitalization… Both are NOT NULL; a blank would fail the insert."
  2. Phase 0 could not run. Report, deviation #1: "The ALPHA_API_KEY in .env is a placeholder… No fixtures were captured from live responses."
  3. Fixtures were invented instead. "Test fixtures were built from Alpha Vantage's published response shapes instead of captured payloads."
  4. The test asserted the wrong scenario. test_missing_market_cap_is_tolerated mocks the key as absent. The real API sends the four-character string "None".
  5. The defect survived to the live database. _optional passes "None" through; Postgres rejects it; Storage catches at batch scope and rolls back — one ETF destroys the whole day's collection.

Findings

Rules — CLAUDE.md

1. Fixtures for third-party APIs may not be written from documentation

This is the single line that would have stopped the chain above. The failure wasn't carelessness — the agent reasoned carefully and hedged well (it handled both Note and Information). What it couldn't do was invent a payload shape it had never seen.

Test doubles for third-party APIs must be built from real captured payloads committed under tests/fixtures/. Never write a mock payload from API documentation or from memory — capture it, commit it, assert against it. If the payload cannot be captured, the work is blocked, not assumed.

The second clause matters as much as the first: it converts "I couldn't verify this" from a footnote in a deviations table into a stop condition.

Build: a CLAUDE.md — this project has none (see finding 2), so this rule is the seed for it.
Rules — CLAUDE.md

2. The project has no rules file at all

No CLAUDE.md, no AGENTS.md, no .claude/rules/. The entire AI layer is one settings.local.json containing a single skill override. Every session re-derived the same facts from scratch — and the run's own "Issues encountered" section is a list of them:

· unittest, not pytest — and discovery only matches test*.py (tests/dags_test.py was silently never collected) · black for formatting; Google-style docstrings · Airflow 2.9 does not support Python 3.12+ — local default is 3.13 · three conflicting Airflow pins (req 2.8.0 / Dockerfile 2.9.0 / CI 2.8.1)

Each of those cost a rediscovery this run. They are exactly what a rules file is for.

Build: run /rules-create-global — it's already installed and designed for precisely this, deriving from the primed codebase.
Skill

3. /piv-validate is still the shipped template

Lines 32–33 of the skill still read # REPLACE: your test command and <your test command>. The skill's own warning — "a checker that cannot fail is worthless" — describes this project's current state.

The consequence is visible in the run: validation was declared complete with "L3 integration — NOT RUN" and "L4 manual validation — NOT RUN", and the pipeline went three full turns before anyone ran it. When it finally was run, every command had to be improvised — in-container unittest, a throwaway container for black, hand-rolled compose polling.

This is also where the run's nastiest near-miss belongs. Second-pass defect #1: the Dockerfile built Python 3.8 while the code uses PEP 585 generics — "Every test passed locally (3.13) and in CI (3.11) while the actual runtime was the one interpreter that breaks." Only a real container run catches that class of bug, and nothing required one.

Build: fill in piv-validate with this project's real commands, and make the container run non-optional:
docker compose up -d --build docker compose exec -T -w /opt/airflow airflow-scheduler python -m unittest discover tests docker compose exec -T airflow-scheduler airflow dags list-import-errors docker run --rm -v "$PWD":/src -w /src python:3.11-slim sh -c "pip install -q black && black --check ."
Highest leverage, lowest effort item on this list.
Rules — CLAUDE.md

4. Two parallel sessions produced two competing ticket breakdowns

Timestamps tell it plainly — one epic, two decompositions, one minute apart, at different granularities and different paths:

21:49 docs/planning/slim-stock-pipeline.md 5 coarse waves (session A) 21:50 docs/planning/tickets/01…24.md 24 fine tickets (session B)

A later planning turn was spent working out which was authoritative, and the two were reconciled by hand into docs/planning/. Nothing about the work was wrong; the two sessions simply had no shared convention for where planning artifacts live.

The same root cause produced a second, smaller cost: a commit was prepared and reported as final while another session was still editing the tree, so it went stale within minutes.

Build: one line in CLAUDE.md — "All planning artifacts live in docs/planning/: PRD, architecture, and tickets/NN-slug.md. Check it before creating any new planning doc."
Hook — PreToolUse

5. Nothing deterministically prevents committing a secret

Ordinarily this would be speculative. It isn't here, for two reasons: a live Alpha Vantage key now sits in .env, a publish remote is configured — and this repository's own history already contains a commit named add AWS credentials that added .env with AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in it.

Protection today is .gitignore plus a detect-private-key pre-commit hook — both of which an agent running git add -f or writing a new file outside the ignore pattern can walk straight past. A PreToolUse hook on Bash is enforcement the agent cannot talk itself out of.

Build: /hooks-create → a PreToolUse hook matching Bash(git add *) and Bash(git commit *) that scans staged content for key-shaped strings and returns permissionDecision: "deny".

Not worth encoding

Two things went wrong that need no rule

The credential investigation. Auto mode's classifier blocked reading secret values out of git history — twice — and the right thing happened: the work stopped and escalated to a human instead of dumping credentials into a transcript. That guardrail already works. Adding a rule here would be cargo cult.

The stale README report. A claim about the tree was accurate when made and false ten minutes later. That isn't a missing rule; it's finding 4 wearing a different hat. Fixing the artifact convention fixes this too — inventing a separate "re-verify before reporting" rule would just add a line nobody reads.
